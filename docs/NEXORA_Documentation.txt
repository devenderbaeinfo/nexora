1. About This Document

This is the master reference for NEXORA -- what it is, why it is built the way it is, and how it will be delivered.
It documents the product identity and design system, the full technical architecture, security and compliance
posture, the complete module surface, and the phase-by-phase development plan, in one place.

This is documentation, not a pitch: every section states what has been decided, what is deferred and why, and
what remains open. Our organization is both the author of this platform and its first production user -- Phase 1 of
the roadmap in Section 14 replaces our own dependency on our existing Zoho ERP environment, while the
architecture underneath is built to extend into a commercial multi-tenant product.

3. Product Vision & Philosophy

Vision: a modern, modular, configurable ERP platform that connects people, processes, finance, projects, and
customers through one secure source of truth -- where an organization activates only the modules it needs, and
nothing more.

  · One source of truth -- no duplicate departmental databases.
  · Integration first -- every module can communicate with every other module by design, not by later

     patchwork.
  · Configuration over customization -- workflows, approvals, roles, policies, and tax rules are configured by an

     administrator, not coded by an engineer.
  · API-first -- every capability is reachable through an API, not locked behind a screen.
  · Security by design -- built into the architecture from the first commit, not added before a compliance audit.
  · Mobile and web from day one -- employees, managers, finance, and administrators, on whichever device

     they are using.
  · Product first -- every internal requirement is tested against one question: is this organization-specific, or

     should it become a configurable platform capability?

7.3 Organizational Data Model

Every table in the schema is designed against this hierarchy from the first migration, even while only one
organization uses the platform. Retrofitting tenant isolation after the fact is one of the most expensive mistakes an
ERP team can make -- so the hierarchy exists in the data model well before multi-tenant rollout is commercially
needed.

7.4 Multi-Tenancy Approach

Multi-tenancy implementation -- tenant sign-up, billing, plan tiers -- can wait until external customers are ready
to onboard. Multi-tenancy architecture cannot wait; it is designed into the schema from Phase 1.

  · Tenant-specific configuration, roles, workflows, branding, localization, and module activation are all
     modeled from the start.

  · A single platform codebase serves every tenant; isolation is enforced at the data layer, not by separate
     deployments per customer.

10. Integration Architecture

An ERP rarely operates in isolation. The integration layer exists from Phase 1, even though most external
integrations themselves are built later.

  · REST APIs, versioned from the first release, so breaking changes never silently affect an existing integration.
  · Webhooks and asynchronous events for systems that need to react to NEXORA activity without polling.
  · Idempotency and retry handling built into the integration layer, so a duplicated request never creates a

     duplicated transaction.
  · API keys and OAuth-based access for external systems, with full integration logging.
  · Planned downstream integrations: payroll providers, banking, email, SSO providers, CRM, tax systems,

     payment gateways, document storage, and BI tools.

11. Reporting & Analytics Architecture

Dashboards are never allowed to run heavy queries directly against transactional tables -- a dedicated reporting
layer exists specifically to keep operational performance and reporting performance independent of each other.

  · HR reporting: headcount, attrition, leave utilization, attendance, overtime.
  · Finance reporting: cash flow, expense trends, budget variance, aging, reimbursement status.
  · Project reporting: budget vs. actual, cost by employee, billable utilization, project profitability.
  · Management reporting: a company-wide dashboard combining financial and operational KPIs across

     departments.

14. Definition of Done -- Worked Example

Every module in this roadmap is only considered complete when it satisfies measurable, testable acceptance
criteria -- not a one-line description. The Leave module is used here as a worked example of the standard applied
to every module.

  · Employee can submit a leave request, including half-day and backdated sick leave.
  · Leave balance is calculated correctly, including partial-day debits.
  · Overlap and blackout-date conflicts are detected before submission.
  · Manager approval and rejection both function and are logged.
  · Cancellation of an already-submitted request is supported.
  · Concurrent requests against the same balance are handled without a race condition.
  · Historical balances are preserved even after an organizational change (department, manager).
  · Every state transition (submit, approve, reject, cancel) writes an audit entry.
  · Notifications fire correctly on every state transition.
   Functional, technical (unit/integration/API/performance tests), security, business (UAT passed, users trained,
   documentation available), and production (monitoring, backups, rollback plan) criteria are all required together --
   a module is not "done" on functional criteria alone.

15. Data Governance & Migration Strategy

Since our organization is the first production customer, migrating cleanly off the existing Zoho environment is
itself a first-class deliverable, not an afterthought.

  · Stage 1 -- Inventory every existing Zoho process: data, users, roles, approvals, reports, integrations, and pain
     points, not just features.

  · Stage 2 -- Build AS-IS and TO-BE process maps for each workflow being migrated.
  · Stage 3 -- For each process, decide: replicate, improve, remove, automate, or generalize into a configurable

     capability.
  · Stage 4 -- Migrate: extract, transform, clean, validate, map, and import -- never a raw CSV export and

     import.
  · Stage 5 -- Run NEXORA and Zoho in parallel to validate before cutover.
  · Stage 6 -- Cut over to NEXORA as the system of record.
  · Stage 7 -- Zoho becomes a read-only archive per an approved retention policy.

20. Closing Statement

NEXORA is not an internal business application that might later become a product. It is a commercial ERP
platform, with our organization serving as its first production environment.

Phase 1 solves our immediate operational requirements and ends our dependency on Zoho. Every subsequent
phase expands the platform toward a complete ERP covering Finance, HR, Procurement, Inventory, Sales,
Projects, Supply Chain, Assets, Analytics, and AI.

The platform's advantage is not the number of screens it has. It is the engine underneath those screens: one
configurable pipeline connecting business rules, approvals, transactions, accounting, audit, and analytics into a
single continuous thread -- from the first policy check to the final ledger entry.
